# DATA LAYOUT

JSON files are organized by entity type, mostly partitioned by brand.

## FILE FORMAT (RFC #45 phase 1)

Every managed data file -- brands, tablets, pens, pen-families,
tablet-families, pen-compat, drivers, pressure-response, pressure-range,
inventory, reference -- is in one canonical format, defined by
formatDataJson() in lib/data-json.ts:

	- UTF-8, no BOM
	- LF line endings (enforced for *.json by .gitattributes)
	- JSON.stringify(value, null, 2) + "
": two-space indent, key order
	  as authored, & / ' / non-ASCII written literally, numbers in
	  shortest form

Tools read with readDataJson() and write with writeDataJson(). Never
hand-roll JSON.stringify, splice text at an indentation, or round-trip
through PowerShell ConvertTo-Json (#43).

	npx tsx scripts/format-data.ts            # check, never writes; exit 1 on issues
	npx tsx scripts/format-data.ts --write    # normalize

Captures keep the bytes their extract scripts produce and are not
managed: otd/, machollywood/, wacom-update/ (including source.xml),
links/, and version.json.

History: the formatting migration was two mechanical commits --
6b237f1 (line endings) and edaa6be (reformat). Both are listed in
.git-blame-ignore-revs, so blame skips them:

	git config blame.ignoreRevsFile .git-blame-ignore-revs

After pulling the line-ending commit into an EXISTING clone, refresh
the working tree once (clean checkout only -- this discards local
changes):

	git rm -r --cached -q data && git reset -q --hard HEAD
	git ls-files --eol data | grep -v "i/lf.*w/lf"   # data/wacom-update/source.xml only

Third-party captures live in their own directories, one per source. These
are mirrors of someone else's published data, kept verbatim and refreshed by
a script; they are never hand-edited, and our reading of them lives in a
separate annotations file rather than in the capture itself.

	/data
		/otd
			otd-tablets.json          OpenTabletDriver configurations
			otd-entity-audit.json
		/machollywood
			machollywood-pen-compat.txt              article text, verbatim
			machollywood-pen-compat.json             structured, lossless
			machollywood-pen-compat-annotations.json our EntityId mapping

Each file wraps its records in a top-level key:
- brands: { "Brands": [...] }
- tablets: { "DrawingTablets": [...] }
- pens: { "Pens": [...] }
- pen-families: { "PenFamilies": [...] }
- tablet-families: { "TabletFamilies": [...] }
- pen-compat: { "PenCompat": [...] } (grouped: PenId -> TabletIds[])
- drivers: { "Drivers": [...] }
- pressure-response: { "PressureResponse": [...] }
- inventory pens: { "InventoryPens": [...] }
- inventory tablets: { "InventoryTablets": [...] }
- defect kinds: { "DefectKinds": [...] }
- iso paper sizes: { "ISOPaperSizes": [...] }
- us paper sizes: { "USPaperSizes": [...] }

Third-party captures do not follow that convention: they mirror a source, so
each keeps whatever shape the capture script produces, with a "source" block
carrying the provenance (URL/commit, retrieval date, content hash).

File naming:
- Most entities: BRAND-entitytype.json (e.g. WACOM-tablets.json)
- Brands: brands.json (single file, not partitioned)
- Inventory: USERNAME-entitytype.json (e.g. sevenpens-pens.json)
- Reference: plain name, not partitioned (e.g. defect-kinds.json)
- Third-party captures: SOURCE-topic.json under /SOURCE (e.g. machollywood/machollywood-pen-compat.json)

See docs/DEFECTS.md for the Defects field on inventory records
and the defect-kinds vocabulary.
